# Technical specification — control plane, data placement and SDK

*Version 0.1 · 2026-10-16 · proposed. Covers milestones M0–M2 of the
[delivery plan](../plan/20-end-to-end-delivery-plan.md). Builds on [doc 02](../plan/02-architecture.md) and
[doc 17](../plan/17-performance-and-concurrency.md); where they describe the full 1.0 system, this document says
what is built first and how. The app-facing part is in the [app integration contract](03-app-integration-contract.md).*

## 1. Components in M0–M2

Deferred until first needed: NATS (webhooks suffice until M5), Temporal (jobs table with `SKIP LOCKED` until
tier moves in M5), OpenFGA (M4), OpenBao (secrets encrypted by a local key-encryption key behind a `KeyManager`
interface until TS17).

## 2. Identifiers and conventions

- All ids are UUIDv7 generated by `maturad`, except user ids, which are Keycloak's user ids (UUID) so `sub` needs no
  mapping.
- Every mutable row has `version bigint` taken from one global sequence `matura_version_seq`; the change feed is
  ordered by it, and apps compare against it (contract §5).
- Times are `timestamptz` UTC. Slugs: `^[a-z0-9](?:[a-z0-9-]{1,38}[a-z0-9])$`, reserved words refused.
- API: JSON, `application/problem+json` errors, cursor pagination (`?cursor=&limit=`), `Idempotency-Key` on POST,
  `If-Match` with `version` on PATCH and DELETE.

## 3. Control-plane schema

Migration `0001_core.sql` (in `internal/store/migrations`). Tenant-owned tables have `tenant_id`, an index leading
with it, and `FORCE ROW LEVEL SECURITY` with the policy below. `maturad` connects as `matura_app` (no `BYPASSRLS`);
migrations run as `matura_owner`.


RLS policy on tenant-owned tables:

```sql
CREATE POLICY tenant_isolation ON workspace
  USING      (tenant_id = nullif(current_setting('matura.tenant_id', true), '')::uuid
              OR current_setting('matura.scope', true) = 'operator')
  WITH CHECK (tenant_id = nullif(current_setting('matura.tenant_id', true), '')::uuid
              OR current_setting('matura.scope', true) = 'operator');
```

Each request opens a transaction and runs `SELECT set_config('matura.tenant_id', $1, true),
set_config('matura.scope', $2, true)` first (safe behind PgBouncer transaction pooling). `scope` is `tenant` for
tenant users and apps, `operator` only for operator tokens; a missing setting returns no rows. `app_user`, `app`,
`app_role`, `plan` and `db_server` are installation-wide and guarded by the API layer (operator scope), not RLS.

## 4. Authentication of callers to `maturad`

| Caller | Credential | Scope |
|---|---|---|
| Console user / end user | Keycloak access token with `aud: matura-api` | tenant from `tid`; tenant role decides what they may change |
| Operator | Keycloak token with realm role `matura-operator` | `operator` scope; every operator action is logged with a reason header for destructive calls |
| App backend | client-credentials token of the app's confidential client | that app only; tenant given per call and checked against `tenant_app` |
| Keycloak SPI | client-credentials token of `matura-keycloak` | internal endpoints `/internal/v1/*` only |

`maturad` verifies tokens with the realm's JWKS (cached, refreshed on unknown `kid`). Local development can run with
`MATURA_AUTH=dev`, which accepts `X-Matura-Dev-User` and `X-Matura-Dev-Scope` headers; the server refuses to start in
that mode unless `MATURA_ENV=development`.

### 5.1 Invitations and email (TS6)

- **Invite** (owners and admins; only owners invite owners): `{email, tenant_role (default member), app_roles:
  [{app, role, workspace_id?}], delivery: "link", deliver_to?}`. App roles are checked up front (app enabled, role
  exists, workspace in the tenant). An active member's address answers 409; an earlier pending invitation to the
  same address is revoked. `delivery: temp_password` answers 422 until it is built.
- **Token:** 32 random bytes, base64url, in the link `MATURA_INVITE_ACCEPT_URL?token=…`; only its SHA-256 is stored.
  Links expire after 7 days (`expires_at`; a pending invitation past it lists as `expired`). The create and resend
  responses carry `accept_url` (not stored) so an admin can pass a link on when email is not set up.
- **Resend** issues a new token and expiry (the old link stops working) and works on pending and expired invitations;
  **revoke** ends a pending one.
- **Accept** (`POST /v1/invitations:accept {token}`, signed in): the token is looked up in operator scope, then the
  rest runs in the invitation's tenant. Refused with **410** when the invitation is accepted, revoked, expired, the
  tenant is not active or the token is unknown ("ask your admin for a new invitation"), and **403** when the
  signed-in email is not the invited one. Otherwise: membership with the tenant role (an existing member keeps theirs),
  the invitation's app roles (one that can no longer be granted is skipped), each other enabled app's default role
  (RL-4), and the invitation marked accepted. Members added directly (`POST …/members`) get default roles too.
  Membership and grant changes reach apps as usual; invitations themselves are not contract events.
- **Accept page:** `GET /invitations/accept` is a self-contained page served by maturad. It shows the tenant and
  address (`/invitations/preview`), signs in or registers (`prompt=create`) at Keycloak with authorization code + PKCE
  as the public client `MATURA_PORTAL_CLIENT_ID` (default `matura-console`, whose redirect URIs must include the
  page), then accepts. It sends no referrer and removes the token from the address bar. The customer portal (TS8)
  can replace it via `MATURA_INVITE_ACCEPT_URL`.
- **Email outbox:** `email_outbox` rows are written in the same transaction as the invitation (anyone may insert;
  only operator scope reads). The mailer (one active replica, advisory lock 7351005) sends due rows over SMTP
  (STARTTLS when offered; credentials only over TLS or to localhost) and retries with backoff (1, 2, 4 … 64 minutes)
  up to 8 attempts, then marks the row `failed`. Without `MATURA_SMTP_ADDR` mail is queued but not sent.

## 6. Token mapper (TS5)

Besides `roles`, the mapper adds `perms`: the union of the permissions of the user's active roles for the calling
app in the token's tenant and workspace, sorted, `["*"]` if any role has `*`. Above 40 entries it adds
`perms_ref: "matura_app_role"` instead (contract §2).

The Java mapper (`keycloak/extensions`, provider id `matura-token-mapper`, attached to each app's client as a
protocol mapper; a realm import that lists its own client scopes would replace Keycloak's built-in ones, such as
`basic`, which carries `sub`) calls `POST /internal/v1/token-context` once per token issue (5-second in-memory cache)
and adds the claims in contract §2. It fails closed: if `maturad` cannot be reached, no token is issued. Tenant
choice comes from the authorisation request parameter `matura_tenant=<slug|id>`, else the user's last-used tenant;
`matura_workspace=<id>` picks a workspace, else the tenant's default. A user without a
membership in the requested tenant gets `access_denied`. A tenant that has not enabled the app gets
`access_denied` with `error_description=app_not_enabled`.

### 6.1 Roles in the manifest and in Matura (ADR 0008)

```yaml
spec:
  permissions:                        # the catalogue: what the app's code checks
    - { name: run.read,  description: See runs }
    - { name: run.start, description: Start a run }
  roles:                              # starter roles; editable in Matura afterwards
    - { name: operator, permissions: [run.read, run.start] }
    - { name: viewer,   permissions: [run.read] }
  defaultRole: viewer
```

A manifest without `permissions` gets a catalogue made of every permission its roles name. Role rows keep `origin`
(`manifest` or `platform`) and `edited`. Re-applying a manifest upserts manifest roles that are not `edited`,
leaves every other role alone, adds new catalogue entries, and fails with the list of roles concerned if it would
remove a permission a role still uses or a role someone holds. A starter role deleted in Matura comes back on the
next apply unless the manifest drops it too.

## 7. Data placement

### 7.1 Modes and managers

| | `manager: app` | `manager: platform` |
|---|---|---|
| `shared` | the app's own database; Matura records `location_label` | Matura creates `<app>_shared` once per server, an owner role and a runtime role without `BYPASSRLS`; every pool tenant gets a placement row pointing at it |
| `schema` | the app creates a schema per tenant | Matura creates `<app>_bridge` once per server, then schema `t_<tenant-slug>` and role `<app>_t_<short-id>` with `USAGE, CREATE` on that schema only and `search_path` set to it |
| `database` | the app creates a database per tenant | Matura creates database `<app>_<tenant-slug>` on a server (dedicated if the plan says so) owned by role `<app>_t_<short-id>`; `CONNECT` revoked from `PUBLIC` |

Names are lower-case, at most 63 bytes, built only from slugs and ids that `maturad` validates, and always quoted
with `pgx.Identifier` when used in DDL.

As built (TS7b, `internal/placement`): database mode names the database `<app>_t_<tenant-slug>` (so a tenant slug can
never collide with `<app>_shared` or `<app>_bridge`). A new placement goes to the active, non-dedicated server with
the fewest placements; shared mode reuses the server that already holds the app's shared database. Dedicated servers
are assigned by operators (M5 moves). A failed step records `error`, sets `failed` and is retried after 1 minute,
doubling to 1 hour. One `maturad` replica provisions at a time (advisory lock 7351004).

### 7.2 Manifest section

```yaml
spec:
  tenancy:
    workspaceScoped: true
    modes: [shared, schema, database]
    managers: [platform, app]
    default: { mode: shared, manager: platform }
    migrations: { trigger: event }        # event: app migrates on placement.provisioned
```

### 7.3 Lifecycle

```
requested ─► provisioning ─► provisioned ─► migrating ─► ready ─► retiring ─► deleted
                 │                │                         │
                 └─► failed ◄─────┘                         └─► moving (M5)
```

1. `tenant_app` is enabled → placement row `requested` with mode and manager from the tenant's plan, else the
   app's default.
2. `platform` manager: a `provision_placement` job creates database/schema/roles idempotently (`IF NOT EXISTS`
   checks, safe to re-run), stores the runtime role password encrypted, sets `provisioned`, writes the outbox event.
   `app` manager: the placement waits in `requested` until the app calls `PUT …/placements/{tid}`, which sets
   `provisioned`.
3. The app receives `placement.provisioned`, asks for credentials if platform-managed, runs its migrations
   (including the contract tables) and calls `POST …:ready`. `maturad` sets `ready`; the mapper's `pmode` claim and
   the SDK's placement cache now route requests there.
4. Requests for a tenant whose placement is not `ready` get `503` with `Retry-After` and problem type
   `tenant-not-ready` from the SDK.
5. Tenant deletion: placement `retiring` → `tenant.deleting` event → the app deletes its data and calls
   `POST …:deleted` → for platform-managed storage, a job drops the schema or database and the role (shared mode:
   the app deleted the rows) → `deleted`.

### 7.4 Credentials

`POST /v1/apps/{app}/placements/{tid}/credentials` returns `{host, port, sslmode, database, user, password,
search_path, mode, expires_at}` for the runtime role; `{"purpose": "migrate"}` returns the role that owns the tables
(`<app>_owner` in shared mode; in schema and database mode the tenant's role owns its schema or database, so it is the
same role). In M1 the password is the placement's stored one and `expires_at` is when the
SDK should ask again (1 h); in M5 OpenBao's database secrets engine issues per-request dynamic roles. The SDK keeps
credentials in memory only.

### 7.5 SDK routing

`matura.tenant_session(principal)`:

- `shared`: one engine for the app's shared database; begins a transaction and runs
  `set_config('matura.tenant_id', tid, true), set_config('matura.workspace_id', wid, true),
  set_config('matura.user_id', uid, true)`.
- `schema`: one engine per database server/database pair, sessions run `SET LOCAL search_path = t_<slug>` and the
  same `set_config` calls (policies stay as a second layer).
- `database`: one engine per tenant database, kept in an LRU (default 200 engines, small pools of 2–5 connections,
  idle engines closed after 10 min). Large installations put PgBouncer in front.

Placement lookups are cached (placement id, mode, server, version) and refreshed by `placement.*` events.

### 7.6 Migrations

The app owns its migrations in every mode. The SDK provides `matura migrate --all-tenants` which walks every
`ready` and `provisioned` placement of the app, runs the app's Alembic upgrade against it (contract tables first),
and reports `ready`. Expand-and-contract migrations are required, since tenants upgrade one after another.

## 8. Outbox, webhooks and change feed

- Every write transaction inserts its change into `outbox` with the same `version` it gave the row.
- The relay (goroutine in `maturad`, one leader by `pg_try_advisory_lock`, sharded later) reads new outbox rows,
  fans out one `webhook_delivery` per subscribed endpoint, and delivers with HMAC signatures, 10 s timeout and
  exponential backoff (1 s → 1 h, 24 h total).
- The change feed reads `outbox` ordered by `id` filtered to tenants that enabled the app; the cursor is the last
  `id`. Outbox rows are kept 30 days (feed horizon); older cursors get `410 Gone` and must take a snapshot.
- Events are filtered per app: an app sees only tenants that enabled it and only its own grants.

## 9. Security

- Secrets (`db_server.admin_secret`, `placement.role_secret`, webhook secrets) are encrypted with AES-256-GCM
  using a data key per row, wrapped by the key-encryption key from `MATURA_KEK` (32 random bytes, base64) through
  the `KeyManager` interface; OpenBao transit replaces it in TS17. Associated data binds each ciphertext to its row id.
- DDL on registered servers runs with identifiers built by `pgx.Identifier{…}.Sanitize()` from validated slugs and
  ids; no user-supplied SQL ever reaches a server.
- Invitation tokens: 32 random bytes, only the SHA-256 is stored, single use.
- Rate limits per tenant and per IP on invitation and sign-up endpoints.
- All operator actions and membership, grant and placement changes are recorded in the outbox (the audit module in
  M3 consumes it).
